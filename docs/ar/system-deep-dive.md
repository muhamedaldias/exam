## 1. الصورة الكاملة في دقيقة

النظام عبارة عن **تطبيق ويب** لإجراء اختبارات إلكترونية محددة بوقت، بطرفين:

| الطرف | من هو | أين يعيش | مثال |
|---|---|---|---|
| **الخادم (Server)** | برنامج بايثون بإطار Django | على جهاز يستقبل الاتصالات (محلياً: نفس جهازك) | يستقبل الإجابات، يحسب الوقت والدرجات |
| **العميل (Client)** | متصفح الويب (Chrome / Edge / Firefox) | على جهاز الطالب أو المعلم | يعرض الأسئلة، يرسل الإجابات |
| **قاعدة البيانات** | ملف SQLite (تطوير) أو خادم Postgres/MySQL (إنتاج) | بجانب الخادم | تحفظ كل شيء: الأسئلة، الجلسات، الدرجات |

```text
┌──────────────┐        HTTP عبر الشبكة         ┌──────────────┐
│    العميل    │  ── طلب Request ───────────▶  │    الخادم    │
│  (المتصفح)   │  ◀── رد Response ───────────  │   (Django)   │
└──────────────┘        البورت 8000             └──────┬───────┘
                                                     │ SQL
                                              ┌──────▼───────┐
                                              │ قاعدة البيانات │
                                              └──────────────┘
```

**الفكرة المحورية التي بُني عليها كل شيء:** المتصفح **غير موثوق**.
أي شيء يحسبه المتصفح (الوقت المتبقي، الدرجة، صحة الإجابة) هو للعرض فقط،
والقرار النهائي دائماً بيد الخادم. هذا هو السبب وراء 90% من التصميم الذي ستراه أدناه.

**دوران العمل باختصار:**

- **المعلم:** يسجّل حساباً ← ينشئ اختباراً ← يقسّم الأسئلة إلى مجموعات (سهل / متوسط / صعب)
  ← يفعّل الاختبار ← يشارك كوداً مثل `QZ-A7K2P9` ← يراقب الطلاب لحظياً ← يصدّر النتائج CSV.
- **الطالب:** يدخل الكود ← يسجّل اسمه ورقمه الجامعي ← يحل الأسئلة والوقت يُحسب من الخادم
  ← تُحفظ إجاباته تلقائياً ← تظهر درجته فور التسليم — **دون أن يحتاج حساباً أصلاً**.

## 2. الخادم Server — من هو وماذا يفعل

### 2.1 من هو الخادم؟

الخادم **ليس جهازاً** — بل هو **برنامج** يعمل باستمرار، يفتح "باباً" (بورت) وينتظر طلبات قادمة،
وعندما يصله طلب يعالجه ويرد عليه ثم يعود للانتظار. في نظامنا الخادم مكتوب بلغة **Python**
وبإطار العمل **Django 5.2**.

**لماذا Python وDjango تحديداً؟**

- Python لغة واضحة وسريعة التطوير، ومكتبات الويب فيها ناضجة ومستقرة.
- Django يقدّم كل ما يحتاجه التطبيق جاهزاً وبطريقة موحدة: توجيه المسارات، نظام المستخدمين،
  لوحة إدارة، حماية CSRF، وطبقة ORM للتعامل مع قاعدة البيانات دون كتابة SQL يدوياً.
- الاعتماديات الكاملة 4 حزم فقط (`Django`, `python-decouple`, `gunicorn`, `mysqlclient`)
  — أي سطح صيانة صغير وتركيب سهل على أي جهاز.

### 2.2 كيف يشتغل الخادم؟ الوضعان: تطوير وإنتاج

الخادم يعمل في وضعين مختلفين تماماً حسب المرحلة:

#### أ) وضع التطوير — خادم Django المدمج

```text
المتصفح ──HTTP──▶ 127.0.0.1:8000 ──▶ manage.py runserver ──▶ كود Django مباشرة
```

- الأمر `python manage.py runserver` يشغّل خادم تجريبي مدمج في Django.
- **ماذا يفعل؟** يستقبل طلبات HTTP على البورت `8000` وينفذ كود المشروع مباشرة،
  ويعيد تحميل نفسه تلقائياً عند تعديل أي ملف — لهذا هو مثالي أثناء البناء والتجربة.
- **لماذا لا يُستخدم في الإنتاج؟** لأنه أحادي الخيط (يعالج طلباً واحداً في كل لحظة)،
  ولا يتحمل ضغط عشرات الطلاب، ولا يخدم الملفات الثابتة بكفاءة، ولا يعيد التشغيل عند السقوط.
- ملف الدخول هنا هو `manage.py` الذي يضبط اسم الإعدادات (`config.settings`) ثم يسلّم المهمة لDjango.

#### ب) وضع الإنتاج — Gunicorn + Nginx (طبقتان)

```text
المتصفح ──HTTP──▶ البورت 80 (Nginx) ──▶ تحويل داخلي ──▶ 127.0.0.1:8000 (Gunicorn ×3) ──▶ Django
```

- **Gunicorn** هو خادم تطبيقات إنتاجي: يشغّل **3 نسخ عاملة (Workers)** من التطبيق،
  فتُعالَج 3 طلبات truly بالتوازي. يُشغَّل بالأمر:
  `gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 3`
  حيث `config/wsgi.py` هو الجسر القياسي (WSGI) بين خادم الويب وكود Django.
- **Nginx** يجلس في المقدمة على البورت `80` (و`443` مع شهادة HTTPS) ويفعل 4 أشياء:
  1. يخدم الملفات الثابتة (`/static/`) مباشرة من القرص دون إزعاج Python — أسرع بعشرات المرات.
  2. يمرّر باقي الطلبات إلى Gunicorn (`proxy_pass http://127.0.0.1:8000`).
  3. يضيف ترويسات أمان (`X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`...).
  4. يضيف عنوان IP الحقيقي للطالب في ترويسة `X-Real-IP` لأن Gunicorn بدونه سيرى كل الطلبات
     قادمة من `127.0.0.1` فقط.
- **لماذا طبقتان وليس Gunicorn وحده؟** لأن Nginx متخصص في ما هو سيئ فيه بايثون:
  الملفات الثابتة، إبطاء العملاء البطيئين (Slow Clients)، وإنهاء TLS — فيبقى Gunicorn حراً
  لمعالجة منطق الاختبارات فقط.

### 2.3 مكونات الخادم الداخلية — ماذا يفعل كل ملف ولماذا

```text
manage.py                  ← بوابة التشغيل (تطوير)
config/
  settings.py              ← كل الإعدادات: السر، قاعدة البيانات، التطبيقات، الجلسات
  urls.py                  ← البوابة الرئيسية: /admin ، /accounts ، وباقي المسارات
  wsgi.py                  ← جسر الإنتاج بين Gunicorn وDjango
accounts/                  ← تطبيق حسابات المعلمين (تسجيل/دخول/تحقق OTP)
quiz/
  models.py                ← هيكل البيانات: 6 جداول (التفاصيل في القسم 4)
  views.py                 ← صفحات HTML: دخول الطالب + لوحة المعلم
  api.py                   ← واجهات JSON: نبض الوقت + حفظ الإجابات + المراقبة
  forms.py                 ← التحقق من مدخلات النماذج قبل لمس قاعدة البيانات
  utils/selection.py       ← خوارزمية اختيار الأسئلة الطبقية
  utils/timer.py           ← سلطة الوقت: حساب المتبقي من السيرفر
  utils/export.py          ← تصدير النتائج CSV
```

| الملف | ماذا يفعل | لماذا وُجد بهذا الشكل |
|---|---|---|
| `settings.py` | يقرأ الأسرار من ملف `.env` (لا تُحفظ في الكود)، يحدد قاعدة البيانات (SQLite للتطوير)، مدة الجلسة 8 ساعات، والإيميل (طباعة على الشاشة في التطوير) | فصل الأسرار عن الكود قاعدة أمنية؛ `.env` يتيح نفس الكود يعمل في كل البيئات |
| `models.py` | يعرّف الجداول الستة وعلاقاتها وقواعدها (مثلاً: منع تكرار نفس الرقم الجامعي في نفس الاختبار) | قاعدة البيانات تُبنى من هذه الأصناف تلقائياً عبر `migrate` — أي تغيير هنا = تغيير حقيقي في التخزين |
| `views.py` | يستقبل طلبات الصفحات، يتحقق من الصلاحيات (`@login_required` للمعلم)، يبني السياق، ويرد بصفحة HTML | فصل "عرض الصفحات" عن "واجهات البيانات" يجعل كل طرف يتطور دون كسر الآخر |
| `api.py` | خمس واجهات JSON تُكلَّم بالجافاسكربت دون تحديث الصفحة (التفاصيل في القسم 6) | الاختبار التفاعلي (حفظ تلقائي + مؤقت حي) مستحيل بتحديث كامل للصفحة كل مرة |
| `forms.py` | يتحقق من كل حقل (الاسم، الرقم، الإيميل، مدة الاختبار...) قبل الحفظ | خط الدفاع الأول ضد المدخلات الفارغة أو الخبيثة قبل وصولها لقاعدة البيانات |

## 3. العميل Client — من هو وماذا يفعل

### 3.1 من هو العميل؟

العميل هو **متصفح الويب** على جهاز المستخدم (طالب أو معلم). لا يحتاج تثبيت أي شيء:
يكتب العنوان، فيستقبل صفحات HTML وملفات جافاسكربت وتنسيقات، ثم ينفذها محلياً.

**التقنيات التي يعمل بها العميل — ولماذا هي بهذه البساطة؟**

| التقنية | دورها | لماذا اختيرت |
|---|---|---|
| HTML + قوالب Django | هيكل الصفحات (نموذج الدخول، ورقة الأسئلة، لوحة المعلم) | تُبنى في الخادم فتصل جاهزة — لا انتظار لتحميل تطبيق |
| Tailwind عبر CDN | التنسيق والألوان والتجاوب مع الجوال | تنسيق احترافي دون خطوة بناء (Build) أو تجميع ملفات |
| Alpine.js عبر CDN | تفاعلات خفيفة (عدّاد، تنقّل بين الأسئلة، نوافذ) | بديل خفيف (كيلوبايتات) عن React/Vue اللذين يحتاجان بناءً معقداً |
| JavaScript خالص (5 ملفات) | منطق الاختبار الحقيقي | تحكم دقيق دون وسيط |
| Lucide عبر CDN | الأيقونات | أيقونات SVG خفيفة بدل الصور |

ملفات الجافاسكربت الخمسة في مجلد `static/js/`:

| الملف | ماذا يفعل بالضبط |
|---|---|
| `timer.js` | يعرض العدّاد التنازلي ويزامنه مع الخادم — **العرض فقط**، القرار للخادم |
| `attempt.js` | إدارة ورقة الاختبار: التنقل بين الأسئلة، جمع الإجابة، إرسالها |
| `autosave.js` | حفظ تلقائي للإجابة فور اختيارها حتى لو انقطع الاتصال ثم عاد |
| `anticheat.js` | المستمعات الأمنية (التفاصيل أدناه) |
| `main.js` | وظائف مشتركة: إرسال الطلبات، قراءة رمز CSRF، رسائل الخطأ |

### 3.2 كيف يشتغل العميل أثناء الاختبار؟

1. **التحميل:** يفتح الطالب رابط الجلسة ← الخادم يرد بصفحة `attempt.html` ومعها أول دفعة أسئلة
   **بدون الإجابات الصحيحة أبداً** — المتصفح لا يعرف الحل ولو فحص الكود.
2. **النبض:** كل 10 ثوانٍ يرسل العميل نبضة `heartbeat` للخادم فيرد بالوقت المتبقي الحقيقي؛
   إن انتهى الوقت يأمر الخادم بالتسليم التلقائي.
3. **الحفظ:** مع كل إجابة يرسل العميل `save-answer` فيحفظ الخادم ويرد إن كانت صحيحة وكم عليها.
4. **المراقبة الذاتية:** مستمعات `anticheat.js` تراقب 5 أحداث وترسلها فوراً:
   `tab_switch` (مغادرة التبويب)، `window_blur` (فقدان تركيز النافذة)،
   `copy_attempt` / `paste_attempt` (منع + تسجيل)، وحجب النقر اليمين واختصارات النسخ وأدوات المطور.
5. **التسليم:** زر تسليم يدوي، أو تسليم تلقائي عند انتهاء الوقت — ثم صفحة النتيجة بالدرجة فوراً.

### 3.3 صفحة المعلم — عميل من نوع آخر

المعلم عميل أيضاً لكن بصلاحيات: لوحته تعرض الاختبارات والجلسات النشطة لحظياً
(تُحدَّث باستدعاء واجهة `live-sessions` دورياً)، ويرى لكل طالب: التقدم، الوقت المتبقي،
الدرجة الحالية، وعدّاد الاشتباه ملوّناً (أخضر 0 / أصفر 1-3 / أحمر 4+).

## 4. قاعدة البيانات — ذاكرة النظام

قاعدة البيانات هي المكان الوحيد الذي "يتذكر" — المتصفح ينسى بإغلاق الصفحة،
والخادم ينسى بإعادة التشغيل، أما هي فتحفظ كل شيء على القرص.

**لماذا SQLite في التطوير وPostgres في الإنتاج؟**
SQLite ملف واحد (`db.sqlite3`) لا يحتاج تثبيت خادم — مثالي للتجربة.
لكنها تقفل الملف كاملاً عند الكتابة، فمع 100 طالب يحفظون معاً تختنق؛
لذلك في الإنتاج يُستخدم Postgres (يدير التزامن والنسخ الاحتياطي باحتراف).

### الجداول الستة وعلاقاتها

```text
Quiz (الاختبار: العنوان، الكود QZ-XXXXXX، المدة، درجة النجاح، التفعيل)
 ├── QuestionGroup (المجموعة: الاسم، درجة السؤال، عدد الأسئلة المختارة pick_count)
 │     └── Question (السؤال: النص، الخيارات، الإجابة الصحيحة)
 └── StudentSession (جلسة طالب: الاسم، الرقم، الإيميل، وقت البدء، الدرجة، قائمة الأسئلة المختارة)
       ├── Answer (إجابة: السؤال، المختار، صح/خطأ، الدرجة، زمن الإجابة)
       └── SuspiciousEvent (حدث اشتباه: النوع، رقم السؤال، الوقت)
```

| الجدول | أهم حقوله | قاعدة ذهبية فيه |
|---|---|---|
| `Quiz` | `quiz_code` فريد، `quiz_duration` بالثواني، `pass_mark`، `is_active` | الكود يُولَّد تلقائياً `QZ-` + 6 رموز ولا يتكرر أبداً |
| `QuestionGroup` | `pick_count` (كم سؤالاً يُسحب من المجموعة لكل طالب) | فريد لكل (اختبار + اسم) — لا مجموعتان بنفس الاسم |
| `Question` | `correct_answer`، الخيارات، المدة الاختيارية للسؤال | الدرجة تُؤخذ من مجموعته، و1 افتراضياً بلا مجموعة |
| `StudentSession` | `selected_question_ids` (نسخة الطالب الخاصة)، `total_score`، `submitted_via` | **فريد لكل (اختبار + رقم جامعي)** — مستحيل أن يختبر نفس الطالب مرتين |
| `Answer` | `is_correct`، `marks_awarded`، `time_taken_seconds` | فريد لكل (جلسة + سؤال) — إجابة واحدة نهائية لكل سؤال |
| `SuspiciousEvent` | `event_type`، `question_index`، `details` | سجل أدلة فقط — لا يعاقب تلقائياً، المعلم يقرر |

## 5. الربط بين العميل والخادم — الرحلة الكاملة لطلب واحد

### 5.1 مثال حي: الطالب يفتح صفحة الدخول بالكود

```text
1) الطالب يكتب في المتصفح:  http://127.0.0.1:8000/QZ-A7K2P9/
2) المتصفح يفتح اتصال TCP مع 127.0.0.1 على البورت 8000 (القسم 8 يشرح كيف)
3) المتصفح يرسل نص HTTP:
     GET /QZ-A7K2P9/ HTTP/1.1
     Host: 127.0.0.1:8000
4) الخادم يستقبل ← يطابق المسار <quiz_code>/ ← ينفذ views.quiz_entry
5) الدالة تسأل قاعدة البيانات: هل يوجد اختبار بهذا الكود وهو مفعّل؟
6) الخادم يبني صفحة HTML (العنوان، المدة، درجة النجاح) ويرد:
     HTTP/1.1 200 OK
     Content-Type: text/html
     <html>...نموذج الاسم والرقم والإيميل...</html>
7) المتصفح يعرض الصفحة. لو الكود خطأ أو الاختبار غير مفعّل: رد 404 (غير موجود).
```

### 5.2 رحلة الطالب الكاملة كسلسلة طلبات

| # | من → إلى | الطلب | ماذا يفعل الخادم | الرد |
|---|---|---|---|---|
| 1 | متصفح → خادم | `GET /QZ-XXXXXX/` | يجلب بيانات الاختبار المفعّل | صفحة الدخول |
| 2 | متصفح → خادم | `POST /QZ-XXXXXX/start/` (الاسم+الرقم+الإيميل) | يتحقق من النموذج، يمنع التكرار، ينشئ الجلسة، **يختار أسئلة هذا الطالب** ويحفظها | تحويل لصفحة الاختبار |
| 3 | متصفح → خادم | `GET /api/session/45/questions/` | يقرأ نسخة الطالب المحفوظة، يخلط الخيارات، **يخفي الإجابات** | JSON بالأسئلة |
| 4 | متصفح → خادم (كل 10 ثوانٍ) | `POST /api/heartbeat/` | يحسب `المدة - (الآن - وقت البدء)`، ويسلّم تلقائياً عند الصفر | الوقت المتبقي |
| 5 | متصفح → خادم (مع كل إجابة) | `POST /api/session/45/save-answer/` | يصحح، يمنح الدرجة، يحدّث المجموع | صح/خطأ + الدرجة |
| 6 | متصفح → خادم (عند الحدث) | `POST /api/session/45/log-suspicion/` | يحفظ حدث الاشتباه | عدّاد الاشتباه |
| 7 | متصفح → خادم | `POST /session/45/submit/` (أو تلقائي) | يغلق الجلسة نهائياً مع سبب التسليم | تحويل للنتيجة |
| 8 | متصفح → خادم | `GET /session/45/result/` | يعرض الدرجة والنسبة وناجح/راسب | صفحة النتيجة |

### 5.3 رحلة المعلم الكاملة

إنشاء الاختبار ← إضافة المجموعات ← إضافة الأسئلة يدوياً ← التفعيل ← مشاركة الكود ←
المراقبة الحية (`live-sessions` تُستدعى دورياً وتعرض كل طالب: التقدم، المتبقي، الاشتباه) ←
النتائج ← تصدير CSV ← تفاصيل كل طالب (إجاباته + أحداثه + زمنه).

## 7. البورتات — أبواب الإرسال والاستقبال

البورت رقم (0-65535) يحدد **أي برنامج** داخل الجهاز يستقبل البيانات القادمة عبر الشبكة.
عنوان IP يوصلك إلى **الجهاز**، والبورت يوصلك إلى **البرنامج** داخله — كرقم الشقة داخل العمارة.

| البورت | من يستمع عليه | متى يُستخدم | لماذا هذا الرقم |
|---|---|---|---|
| **8000** | خادم التطبيق (runserver للتطوير / Gunicorn للإنتاج) على `127.0.0.1` | دائماً — كل طلبات النظام تمر هنا | عُرف شائع لخوادم التطوير؛ فوق 1024 فلا يحتاج صلاحيات مدير |
| **80** | Nginx في الإنتاج | واجهة العالم الخارجي (HTTP) | البورت القياسي للويب — المتصفح يفترضه عند كتابة domain دون رقم |
| **443** | Nginx في الإنتاج مع شهادة | نفس 80 لكن مشفّراً (HTTPS) | البورت القياسي للويب المشفر |
| **5432** | خادم Postgres في الإنتاج | عندما يكلّم Django قاعدة البيانات | البورت الافتراضي لPostgres |
| **3306** | خادم MySQL (بديل مدعوم) | بديل Postgres عند الحاجة | البورت الافتراضي لMySQL |

**ملاحظة مهمة عن `127.0.0.1`:** اسمه "الحلقة المحلية" (Loopback) — عنوان يعني "نفس هذا الجهاز"،
لا يخرج للشبكة أبداً. لذلك `http://127.0.0.1:8000/` يعمل على جهازك فقط، وهذا مقصود في التطوير:
باب مغلق على العالم الخارجي. أما في الإنتاج فيُربط Gunicorn بـ `0.0.0.0` (كل الواجهات)
ويتصدر Nginx المشهد ليستقبل من الجميع.

## 8. البروتوكولات المستخدمة — لغة التخاطب

البروتوكول اتفاقية دقيقة: "كيف نبدأ الكلام، وكيف ننهيه، وماذا تعني كل رسالة".
الطلب الواحد يمر بطبقات فوق بعضها — كل طبقة تخدم التي فوقها:

```text
┌─────────────────────────────┐
│  HTTP      طلب/رد الويب     │  ← المتصفح وDjango يتكلمان بها
├─────────────────────────────┤
│  TLS       التشفير (إنتاج)  │  ← تحمي HTTP من التنصت
├─────────────────────────────┤
│  TCP       التوصيل الموثوق  │  ← يضمن وصول كل بايت وبالترتيب
├─────────────────────────────┤
│  IP        العنونة والتوجيه │  ← يوصل الحزم للجهاز الصحيح
└─────────────────────────────┘
```

### 8.1 TCP/IP — أساس كل شيء (لماذا نحتاجه؟)

- **IP:** يعرّف عنوان كل جهاز (مثل `127.0.0.1`) ويوجّه الحزم (Packets) عبر الشبكة.
  بلا IP لا يعرف المتصفح أين يرسل.
- **TCP:** يقسّم الرسالة لحزم صغيرة، يرقّمها، ويعيد إرسال ما ضاع — فيصل الطلب **كاملاً ومرتباً
  وبدون أخطاء**. بلا TCP قد تصل الإجابة ناقصة أو مقلوبة فيحسب الخادم درجة خاطئة.
- قبل أي كلام ويب، يجري **المصافحة الثلاثية**: `SYN ← SYN-ACK ← ACK` — اتفاق "هل تسمعني؟ نعم، وأنت؟"
  ثم يبدأ الحديث، ثم يُغلق الاتصال بنظام. كل هذا يحدث في أجزاء من الثانية.

### 8.2 DNS — دفتر الهواتف

يحوّل الأسماء (`example.com`) إلى عناوين IP. محلياً لا نحتاجه لأننا نستخدم `127.0.0.1`
و`localhost` مباشرة، وفي الإنتاج يُشترى نطاق ويُربط بعنوان الخادم.

### 8.3 HTTP/1.1 — بطل القصة (ماذا يفعل؟ كيف يشتغل؟ لماذا؟)

**ماذا هو؟** بروتوكول نصي بسيط: العميل يرسل **طلباً** (سطر + ترويسات + جسم اختياري)،
والخادم يرد **بردّ** (حالة + ترويسات + جسم). ثم ينتهي كل شيء — **لا يتذكر الخادم شيئاً
بين طلب وآخر** (Stateless)، وهذا سبب اختراع الكوكيز والجلسات أدناه.

**طرق الطلب المستخدمة في النظام (Methods) — ولماذا وُزعت هكذا؟**

| الطريقة | معناها | أين تُستخدم | لماذا؟ |
|---|---|---|---|
| `GET` | "أعطني" — قراءة فقط، بلا آثار جانبية | عرض الصفحات، تحميل الأسئلة، المراقبة | آمنة وقابلة للتحديث والمشاركة |
| `POST` | "نفّذ" — عملية تُغيّر شيئاً | بدء الجلسة، حفظ إجابة، نبضة، تبليغ اشتباه، التسليم | لأنها تُنشئ/تُعدّل بيانات، والمتصفح يحذّر قبل إعادة إرسالها |

**رموز الحالة (Status Codes) التي يرد بها الخادم:**

| الرمز | معناه | مثال في النظام |
|---|---|---|
| `200 OK` | نجح الطلب | صفحة عُرضت، نبضة ردّت بالوقت |
| `302 Redirect` | "اذهب لعنوان آخر" | بعد بدء الجلسة ← تحويل لصفحة الاختبار؛ الغريب ← تحويل للدخول |
| `400 Bad Request` | طلب ناقص/خاطئ | حفظ إجابة دون `question_id`، أو بعد انتهاء الوقت |
| `404 Not Found` | لا يوجد هذا الشيء | كود اختبار وهمي، أو جلسة مسلّمة يُطلب تحميل أسئلتها |
| `500 Error` | عطل داخلي | استثناء غير متوقع (يُسجَّل ويُعالَج) |

**أهم الترويسات (Headers) — بطاقات تعريفية على كل رسالة:**

| الترويسة | الاتجاه | ماذا تفعل |
|---|---|---|
| `Host` | عميل → خادم | اسم الجهاز المطلوب (به يعرف Nginx أي موقع يقصد إن استضاف عدة مواقع) |
| `Content-Type: application/json` | عميل → خادم | "الجسم القادم JSON وليس نموذجاً عادياً" — به يعرف الخادم كيف يفكّه |
| `X-CSRFToken` | عميل → خادم | إثبات أن الطلب صادر من صفحاتنا فعلاً (التفاصيل في 8.6) |
| `Cookie: sessionid=...` | عميل → خادم | هوية المعلم — "أنا فلان الذي سجّل دخوله" (التفاصيل في 8.5) |
| `Set-Cookie` | خادم → عميل | "احفظ هذه الهوية وأرسلها مع كل طلب قادم" |
| `X-Real-IP` | Nginx → Gunicorn | عنوان الطالب الحقيقي بعد أن حجبه التحويل الداخلي |

### 8.4 HTTPS/TLS — متى ولماذا التشفير؟

محلياً (`127.0.0.1`) الحركة لا تغادر جهازك فلا حاجة للتشفير.
في الإنتاج يُفعَّل HTTPS على البورت 443: طبقة TLS تُشفّر كل بايتات HTTP فلا يستطيع
متلصص على الشبكة قراءة الإجابات أو سرقة كوكي المعلم — دون تغيير أي سطر في كود التطبيق،
لأن التشفير يحدث في Nginx قبل وصول الطلب لPython.

### 8.5 الكوكيز والجلسات — كيف يتذكر الخادم "من أنت" وهو نسّاء بطبعه؟

بما أن HTTP لا يتذكر، تُحل المشكلة بسوار معصم:

1. يسجّل المعلم دخوله (اسم + كلمة مرور صحيحة).
2. ينشئ الخادم **جلسة** (Session) برقم عشوائي طويل `sessionid` ويحفظها في قاعدة البيانات
   مربوطة بحساب المعلم، ويرد بترويسة `Set-Cookie: sessionid=abc123`.
3. يحفظ المتصفح السوار، ويرفقه تلقائياً (`Cookie: sessionid=abc123`) مع **كل** طلب لاحق.
4. الخادم يقرأ السوار، يبحث عنه في جدول الجلسات، فيعرف "هذا المعلم فلان" —
   وبه يحمي كل مسارات `/teacher/...` (بلا سوار صالح ← تحويل للدخول).
5. الجلسة هنا تعيش 8 ساعات (`SESSION_COOKIE_AGE`) وتتجدد مع كل طلب، ولا تُقرأ بجافاسكربت
   (`HTTPONLY`) فلا يسرقها كود خبيث.

أما الطالب فلا حساب له أصلاً: هويته هي **رقم الجلسة في الرابط** (`/session/45/attempt/`)
مع قاعدة "رقم جامعي واحد = جلسة واحدة لكل اختبار".

### 8.6 CSRF — لماذا يرفض الخادم طلبات تبدو سليمة؟ وكيف يمررها صاحبها؟

**المشكلة:** المتصفح يرفق الكوكيز تلقائياً مع أي طلب — حتى لو صدر من موقع شرير!
فصفحة خبيثة قد ترسل `POST /submit/` باسم معلم مسجّل دخوله دون علمه (هجوم CSRF).

**الحل المطبق:** سرّ مزدوج لا يعرفه المهاجم:

1. الخادم يزرع رمزاً سرياً (`csrftoken`) في كل صفحة عبر وسم القالب.
2. كود الجافاسكربت يقرأ الرمز من الصفحة ويرفقه يدوياً بترويسة `X-CSRFToken` مع كل طلب `POST`.
3. الخادم يقارن الرمز المرفق بالمخزّن في الجلسة — متطابق ← يُنفَّذ، مختلف/غائب ← رفض `403`.
4. المهاجم لا يستطيع قراءة الرمز (سياسة نفس-المنشأ تمنع موقعاً من قراءة صفحات موقع آخر)،
   فيفشل هجومه حتى مع وجود الكوكيز. لهذا كل واجهات `api.py` محمية بـ `@csrf_protect`.

### 8.7 WSGI — الجسر بين عالمين

Gunicorn يتكلم شبكات، وDjango يتكلم بايثون — وWSGI هو العقد القياسي بينهما:
يحوّل Gunicorn الطلب الشبكي لكائن بايثون، ينادي الدالة `application` في `config/wsgi.py`،
ويعيد الردّ لصيغة شبكية. بفضله تستطيع استبدال Gunicorn بأي خادم آخر دون لمس كود التطبيق.

### 8.8 JSON — صيغة الكلام بين الجافاسكربت والخادم

الصفحات تُنقل HTML، لكن واجهات AJAX تتكلم JSON — نص خفيف يفهمه الطرفان:

```json
// الطالب يرسل إجابة:
{ "question_id": 12, "chosen_answer": "option_b", "time_taken": 23 }

// الخادم يرد:
{ "status": "saved", "is_correct": true, "marks_awarded": 3, "total_score": 15 }
```

**لماذا JSON وليس غيره؟** تقرأه الجافاسكربت بسطر واحد، ويقرأه بايثون بسطر واحد،
وحجمه صغير — مثالي لنبضة كل 10 ثوانٍ وحفظ كل إجابة دون إبطاء الاختبار.

## 9. كيف تُرسل الطلبات وكيف تُستقبل — خطوة بخطوة

### 9.1 الإرسال من العميل: سطر واحد يفعل الكثير

```javascript
fetch("/api/session/45/save-answer/", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",   // أخبر الخادم أن الجسم JSON
    "X-CSRFToken": getCookie("csrftoken") // إثبات أنني من صفحات النظام
  },
  body: JSON.stringify({                   // تحويل الكائن لنص JSON
    question_id: 12,
    chosen_answer: "option_b",
    time_taken: 23
  })
});
```

ما يحدث تحت الغطاء: المتصفح يفتح TCP (أو يعيد استخدام اتصال مفتوح)، يكتب نص HTTP كاملاً
(السطر + الترويسات + الجسم) ويرفقه تلقائياً بكوكيز النطاق، ثم ينتظر الرد ويحوّله لكائن
يحدّث به الصفحة (علامة ✓، الدرجة الجديدة) — كل ذلك **دون تحديث الصفحة**.

### 9.2 الاستقبال في الخادم: 6 محطات يمر بها كل طلب داخل Django

```text
TCP/HTTP
  │  1) خادم الشبكة (runserver/Gunicorn) يفكّ البايتات لطلب HTTP
  ▼
Middleware (البوابات الأمنية بالترتيب)
  │  2) الأمان ← الجلسات (قراءة sessionid ومعرفة المستخدم) ← التحقق CSRF ← تسجيل الدخول
  ▼
URL Resolver (موظف الاستقبال)
  │  3) يقارن المسار بقوائم config/urls.py ثم quiz/urls.py ثم accounts/urls.py
  │     "api/session/45/save-answer/" ← تطابق ← الدالة api.save_answer مع session_id=45
  ▼
View/API (الموظف المختص)
  │  4) save_answer: هل الجلسة مسلّمة؟ هل انتهى الوقت؟
  │     هل السؤال يتبع نفس الاختبار؟ صحّح، امنح الدرجة، حدّث المجموع
  ▼
ORM → Database (أمين الأرشيف)
  │  5) تُترجم العمليات لأوامر SQL وتُنفَّذ على SQLite/Postgres
  ▼
Response (الرد)
   6) يُبنى JSON + رمز الحالة 200 ويعود بنفس الطريق عكسياً للمتصفح
```

### 9.3 مثال مفصّل: نبضة الوقت `heartbeat`

1. مؤقت الجافاسكربت يطلق `fetch("/api/heartbeat/", {method:"POST", body:'{"session_id":45}'})` كل 10 ثوانٍ.
2. تصل للخادم ← تمر عبر الـMiddleware ← تصل الدالة `heartbeat`.
3. الدالة تجلب الجلسة 45 من قاعدة البيانات.
4. إن كانت مسلّمة ← رد `{status:"submitted"}` فيتوقف العميل عن النبض.
5. وإلا تحسب: `المتبقي = مدة الاختبار − (الآن − وقت البدء)` — **بساعة الخادم دائماً**.
6. إن نفد الوقت: تُغلق الجلسة (`is_submitted=True, submitted_via="auto_quiz"`) ويرد
   `{status:"auto_submitted"}` فيحوّل العميل الطالب لصفحة النتيجة فوراً.
7. وإلا: رد `{status:"ok", time_remaining: 742}` فيحدّث العدّاد العرض فقط.

**الخلاصة الأمنية:** حتى لو عبث الطالب بعدّاد المتصفح أو أوقف الجافاسكربت كلياً،
الجلسة تُغلق في الخادم في موعدها — لأن الخادم لا يسأل العميل "كم بقي؟" بل يحسبها بنفسه.

## 10. الخوارزميات الداخلية — عقل النظام

### 10.1 اختيار الأسئلة الطبقي — عدالة النسخ المختلفة

**المشكلة:** نريد كل طالب نسخة مختلفة (لمنع الغش بالنقل) لكن بنفس مستوى الصعوبة (للعدالة).
العشوائية العمياء قد تعطي طالباً كل الأسئلة سهلة وآخر كلها صعبة.

**الحل (ملف `utils/selection.py`):** العشوائية الطبقية — اسحب عشوائياً **داخل** كل مستوى:

```text
لكل مجموعة (سهلة/متوسطة/صعبة) بالترتيب:
    اسحب pick_count أسئلة عشوائياً من أسئلة هذه المجموعة فقط
اجمع المسحوبات ← اخلط ترتيبها النهائي (إن فُعِّل الخلط)
البذرة = رقم الجلسة → نفس الطالب يرى نفس النسخة دائماً، وطالب آخر يرى غيرها
```

مثال: مجموعة "سهل: اسحب 6 من 12" + "متوسط: اسحب 3 من 8" ← كل طالب 9 أسئلة مختلفة
لكنها دائماً 6 سهلة + 3 متوسطة. وتُحفظ نسخة كل طالب (`selected_question_ids`) فلا تتغير عليه أبداً.

### 10.2 التصحيح والدرجات

عند حفظ كل إجابة: يُطبَّع الجواب (`A` ← `option_a`) ويُقارن بالصحيح ←
صحيحة: يمنح درجة السؤال (من مجموعته)، خاطئة: صفر ← يُعاد حساب `total_score` كمجموع فعلي
من جدول الإجابات (لا كرقم متراكم قد يخطئ) ← النسبة = المجموع ÷ الأعلى × 100 ←
ناجح إن بلغت `pass_mark`.

### 10.3 نقاط الاشتباه — أدلة لا أحكام

كل حدث (تبديل تبويب، فقدان تركيز، نسخ، لصق، اختصار محظور) يُحفظ مع رقم السؤال ووقته.
العدّاد الكلي يلوَّن: `0 أخضر نظيف` / `1-3 أصفر بسيط` / `4+ أحمر مرتفع` —
ويبقى القرار للمعلم بعد مراجعة السياق (طالب سريع الإجابة مع أحداث كثيرة ≠ طالب فتح نافذة بالخطأ).

## 11. لماذا صُمم هكذا — فلسفة التصميم

| القرار | السبب العميق |
|---|---|
| الخادم صاحب الوقت والتصحيح | المتصفح تحت سيطرة الطالب — أي حساب فيه قابل للتزوير، فالحقيقة الوحيدة هي ساعة وقاعدة الخادم |
| لا حسابات للطلاب | كل حاجز إضافي (كلمة مرور منسية، تفعيل إيميل) يعني طلاباً لا يدخلون الاختبار؛ الهوية الكافية هي الرقم الجامعي الفريد |
| منع المحاولة المكررة على مستوى قاعدة البيانات (وليس الكود فقط) | قيد `UNIQUE` لا يمكن تجاوزه بطلبين متزامنين — الكود قد يخطئ، القيد لا يخطئ |
| الإجابات الصحيحة لا تغادر الخادم أبداً | لو وصلت للمتصفح لاستخرجها أي طالب من أدوات المطور في ثانية |
| الأحداث أدلة لا عقوبات تلقائية | النظام لا يستطيع التمييز بين الغش وطفل أغلق التبويب بالخطأ — فالآلة تجمع والإنسان يحكم |
| 4 اعتماديات فقط وبدون بناء واجهات | كل مكتبة إضافية = ثغرة محتملة + تعقيد تركيب على أجهزة المدارس البسيطة |
| SQLite للتطوير وPostgres للإنتاج | ابدأ بأخف شيء يعمل، وانتقل للأقوى عندما يأتي الضغط الحقيقي |

## 12. التشغيل المحلي للنظام

المتطلبات: Python 3.11+ على الجهاز، ولا حاجة لأي خادم خارجي.

```bash
# 1) إنشاء بيئة معزولة وتثبيت الاعتماديات
python -m venv venv
venv\Scripts\activate          # Windows
pip install Django python-decouple

# 2) ملف الإعدادات المحلية (يُنشأ مرة واحدة)
# ملف .env يحتوي:
#   SECRET_KEY=<مفتاح عشوائي طويل>
#   DEBUG=True
#   ALLOWED_HOSTS=localhost,127.0.0.1
#   DB_ENGINE=django.db.backends.sqlite3
#   DB_NAME=db.sqlite3

# 3) بناء قاعدة البيانات
python manage.py migrate

# 4) حساب المعلم
python manage.py createsuperuser

# 5) التشغيل — يستمع على http://127.0.0.1:8000/
python manage.py runserver
```

ثم: صفحة الطلاب `http://127.0.0.1:8000/` — ودخول المعلم `/accounts/login/`.

## 13. قاموس المصطلحات

| المصطلح | معناه بجملة |
|---|---|
| خادم Server | برنامج ينتظر طلبات على بورت ويرد عليها |
| عميل Client | الجهة التي تطلب (هنا: المتصفح) |
| بورت Port | رقم الباب الذي يستمع عليه برنامج داخل الجهاز (8000 للتطبيق، 80 للويب، 443 للمشفر، 5432 لPostgres) |
| بروتوكول Protocol | اتفاقية دقيقة لشكل الرسائل ومعانيها |
| TCP | توصيل مضمون: كل البيانات تصل كاملة ومرتبة |
| IP | عنوان الجهاز في الشبكة |
| DNS | دفتر يحوّل الأسماء لعناوين IP |
| HTTP | لغة الويب: طلب من عميل ورد من خادم |
| HTTPS/TLS | نفس HTTP لكن مشفّر ضد التنصت |
| WSGI | الجسر القياسي بين خادم الشبكات وكود بايثون |
| ORM | كتابة عمليات قاعدة البيانات بأصناف بايثون بدل SQL |
| جلسة Session | سوار `sessionid` يتذكر به الخادم المستخدم بين الطلبات |
| CSRF | هجوم ينتحل هوية مسجّل الدخول — يُصَدّ برمز سري مزدوج |
| JSON | صيغة نصية خفيفة لتبادل البيانات بين الجافاسكربت والخادم |
| Endpoint | عنوان مسار محدد يقدم وظيفة محددة (مثل حفظ إجابة) |
| Stateless | الخادم لا يتذكر بين طلب وآخر إلا ما حُفظ صراحة |
| Worker | نسخة عاملة من التطبيق تعالج طلباً بالتوازي مع أخواتها |

---

*نهاية الوثيقة — تغطي: الخادم (من هو/كيف يشتغل/ماذا يفعل/لماذا)، العميل (ماذا يفعل/كيف يشتغل)،
الربط بينهما (البورت 8000 وبروتوكول HTTP فوق TCP/IP)، الإرسال والاستقبال (fetch ← Middleware ← URLs ←
Views ← ORM ← Response)، والخوارزميات والفلسفة والتشغيل.*
